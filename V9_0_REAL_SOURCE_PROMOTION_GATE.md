## 3. Promotion State Machine

The promotion gate enforces a deterministic 4-state transition machine. Direct state jumps (such as `PILOT_ELIGIBLE -> APPROVED_FOR_PRODUCTION`) are strictly prohibited and raise `InvalidStateTransitionError`.

```
                    ┌─────────────────────────┐
                    │     PILOT_ELIGIBLE      │
                    └────────────┬────────────┘
                                 │
                     [Successful Pilot Run]
                                 │
                                 ▼
                    ┌─────────────────────────┐
                    │     PILOT_VERIFIED      │
                    └────────────┬────────────┘
                                 │
                     [Promotion Gate Invocation]
                                 │
                                 ▼
                    ┌─────────────────────────┐
                    │   PROMOTION_PENDING     │
                    └──────┬───────────┬──────┘
                           │           │
            [All 20 Criteria Pass]     [Critical Blocker / Reject]
            [Including Human Signoff]   │
                           │           ▼
                           │    ┌──────────────┐
                           │    │   REJECTED   │
                           ▼    └──────────────┘
            ┌───────────────────────────┐
            │  APPROVED_FOR_PRODUCTION  │
            └───────────────────────────┘
```

### Transition Validation Rules
1. **`PILOT_ELIGIBLE -> PILOT_VERIFIED`**: Requires a completed pilot run with validated provenance (`REMOTE_SOURCE_DATA`), valid upstream numeric revisions, and a signed pilot manifest.
2. **`PILOT_VERIFIED -> PROMOTION_PENDING`**: Requires initiation of promotion evaluation and verification that all input pilot artifacts are intact.
3. **`PROMOTION_PENDING -> APPROVED_FOR_PRODUCTION`**: Requires 100% PASS across all 20 promotion checklist items, including human legal signoff on any flagged licensing boundaries.
4. **`PROMOTION_PENDING -> REJECTED`**: Triggered if any critical blocker occurs (e.g. invalid license, secret credential detected, benchmark contamination, or corrupted shard).

## 6. Promotion Accounting & Conservation Equations

The promotion subsystem tracks every document and token using [`training/acquisition/promotion_accounting.py`](file:///C:/Users/L.Thirumala%20Teja/OneDrive/Desktop/Nirmal%201/training/acquisition/promotion_accounting.py).

### Exact Conservation Equations
1. **Document Conservation:**
   $$\text{pilot\_verified\_documents} = \text{promoted\_documents} + \text{promotion\_rejections}$$
2. **Token Conservation:**
   $$\text{pilot\_verified\_tokens} = \text{promoted\_tokens} + \text{promotion\_rejected\_tokens}$$

### Non-Anonymous Data Mandate
Every promoted record is required to possess a complete provenance tuple:
```json
{
  "source_id": "wikipedia_open_corpus",
  "page_id": 24898,
  "revision_id": 1243544521,

```
Any promoted record lacking a non-empty `source_id`, `page_id`, `revision_id`, `document_hash`, or manifest reference raises `AnonymousPromotedDataError` and halts execution.

## 7. Idempotency & Replay Protection

To prevent accidental dataset duplication across batch runs or multi-node acquisitions, the promotion gate implements deterministic identity resolution:
$$\text{PromotionKey} = f'\{\text{source\_id}\}:\{\text{page\_id}\}:\{\text{revision\_id}\}'$$

- **First Promotion:** Evaluates all 20 criteria; if passed, records the key into `data/promotion/verified/promoted_registry.json` and returns `ACCEPT`.
- **Identical Re-promotion:** Encountering an existing key with the same revision returns `REJECT_DUPLICATE` (classified as `replay_duplicate_promoted`), rejecting the duplicate without writing tokens.
- **Revision Bump:** Encountering an existing page with a newer upstream revision identifier produces a new unique key and is processed as `NEW_VERSION`.

---

## 8. Rollback Verification

The promotion gate provides a non-destructive rollback facility via `rollback_promotion(promotion_id)`:
1. **Verified Artifact Removal:** Deletes only the specific promoted shard file and manifest from `data/promotion/verified/` and `data/promotion/manifests/`.
2. **Audit Trail Preservation:** Writes an immutable audit record to `data/promotion/reports/rollback_<promotion_id>.json`.
3. **Pilot & Production Safety:** Leaves all files in `data/pilot/` and `data/shards/` untouched.
4. **Registry Reversal:** Atomically removes rolled-back keys from `promoted_registry.json`.

## 9. Human Review Boundary

The promotion gate formalizes the legal and policy boundary separating deterministic code execution from human legal deliberation.

When a candidate source presents unresolved legal questions (such as Creative Commons Share-Alike provisions), the gate writes a structured JSON record into `data/promotion/human_review/`:

```json
{
  "issue_id": "wikipedia_open_corpus_cc_by_sa_legal_boundary",
  "question": "Does CC-BY-SA 4.0 copyleft apply to downstream neural network model weights?",
  "source_id": "wikipedia_open_corpus",
  "evidence_reference": ".../data/source_evidence/wikipedia_open_corpus.json",
  "reason_software_cannot_decide": "Copyright status of generative AI model weights trained on CC-BY-SA text is an unsettled legal question requiring human legal counsel signoff.",
  "review_status": "NEEDS_HUMAN_REVIEW",
  "timestamp": "2026-09-08T16:27:55Z"
}
```

### Prohibition Against Software Auto-Approval
Software is strictly prohibited from mutating `NEEDS_HUMAN_REVIEW` into `APPROVED`. Only explicit human operator input (via the `--force-human-approval` CLI flag with an audited authorization credential) can advance the status past the boundary.
